# 게시판 검증 절차

`.agents/roles/board-validator.md`의 역할 지침을 먼저 읽고, `AGENTS.md`, `docs/engineering-playbook.md`, `docs/quality-agents.md`를 따른다. 요청 범위에 맞는 백엔드·프론트 계약, API 테스트 시나리오, 명세·테스트 추적표를 확인한다.

1. 범위와 소스 상태를 기록한다. Git 메타데이터를 사용할 수 없으면 확인 가능한 파일과 한계를 적는다.
2. 시나리오별 계약·구현·기존 테스트의 실제 assertion을 대조한다. 미정 정책은 `DECISION_NEEDED`로 둔다.
3. 테스트 에이전트에 보낼 계획을 만든다. 시나리오 ID, 입력·사전 조건, 기대 동작, 테스트 계층, 관찰 가능한 합격 기준, 우선순위를 포함한다. 정상·비인증·권한 없음·입력 실패·경계 조건을 범위에 맞게 고른다.
4. 테스트 결과가 오면 실행한 소스 버전과 환경, assertion, 리포트와 산출물을 직접 확인한다. 이후 소스가 바뀌었으면 영향을 받는 증거를 다시 요청한다.
5. 결함, 정적 위험, 커버리지 공백, 환경 장애를 구분해 최종 판정한다. 빠진 테스트만으로 제품 결함을 확정하지 않는다.

H2 테스트는 PostgreSQL의 마이그레이션·제약·트리거·동시성 증거가 아니다. `EDGE-26`, `EDGE-27`에는 실제 PostgreSQL 증거가 필요하다. 관리자 메뉴 노출 여부는 서버 API 권한 확인을 대신하지 않는다. 서버 HTTP 응답은 DB와 전체 기능의 정상 동작을 뜻하지 않는다. `SKIPPED`, `BLOCKED`, `NOT RUN`을 `PASS`로 올리지 않는다.

부모가 지정한 `docs/validation/<실행 ID>/`에 `validation-plan.md`, `validation-review.md`를 작성한다. 최종 보고에는 범위, 근거가 있는 파일 위치, 미해결 항목과 재개 조건을 포함한다. 제품 코드·테스트·계약은 수정하지 않는다. 같은 장애가 새 근거 없이 두 번 반복되면 재개 조건을 보고하고 나머지 독립 검토를 마친다.
