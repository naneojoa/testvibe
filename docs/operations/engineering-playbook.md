# 개발·검토 작업 지침

## 목적

프로젝트 전체에서 사용하는 구현·검토 지침이다. 반복해서 적용할 작업 규칙을 정하며, API와 사용자 경험의 상세 계약은 `../contracts/backend-api-spec.md`와 `../contracts/front-spec.md`를 기준으로 한다.

## 코드 변경 전 확인

1. 관련 API·화면 계약과 시나리오 ID를 읽는다.
2. 상태를 관리할 위치를 정한다. 컴포넌트 내부, Zustand 클라이언트 상태, TanStack Query 서버 상태, 데이터베이스 중에서 구분한다.
3. 결정되지 않은 제품·운영 사항은 `DECISION_NEEDED`(결정 필요)로 표시한다. 계약을 임의로 추정하지 않는다.
4. 의도한 동작을 입증할 수 있는 가장 적은 비용의 회귀 테스트를 추가하거나 갱신한다.

## 프론트엔드 규칙

- 경로별 화면 구성은 `src/pages`, 도메인별 API 함수는 `src/features/*/api.ts`, 공통 HTTP·검증·형식 변환은 `src/lib`, 재사용 UI는 `src/components`에 둔다.
- API 데이터는 TanStack Query로 관리한다. 데이터 변경에 성공하면 영향을 받는 모든 쿼리를 무효화하거나 갱신한다.
- Zustand는 현재 사용자와 토스트처럼 여러 화면에서 공유하는 클라이언트 상태에만 사용한다. 게시글·댓글을 중복 저장하지 않는다.
- 폼 입력, 진행 중인 대화상자, 임시 편집 상태는 컴포넌트 내부 상태로 관리한다.
- 모든 API 요청은 `lib/api.ts`를 거친다. 페이지나 기능 컴포넌트에서 `fetch`를 직접 호출하지 않는다.
- 사용자에게 안전한 오류 메시지를 표시한다. 예상하지 못한 오류의 `requestId`는 보존하고, 스택 추적 정보나 비밀값은 표시하지 않는다.
- 의미 있는 레이블·역할·화면 표시 문구를 우선 사용한다. 테스트가 CSS 구현 세부사항에 의존해서는 안 된다.

## 백엔드와 계약 규칙

- API 계약을 변경할 때 `../contracts/backend-api-spec.md`, TypeScript DTO, 입력 검증, 테스트를 같은 작업에서 갱신한다.
- API 경계에는 DTO를, 트랜잭션 경계에는 Service를 사용한다. 목록·검색 조회에는 QueryDSL을 사용하고, 스키마 변경은 Flyway로만 수행한다.
- 이미 적용한 Flyway 마이그레이션은 수정하지 않는다. 새 버전의 마이그레이션을 추가한다.
- 인증·권한 관련 UI는 사용자 편의를 위한 것이다. 실제 접근 허용 여부는 Spring Security와 Service 계층의 검사를 기준으로 판단한다.

## 테스트 계층 선택 기준

| 변경 사항 또는 위험 | 우선 사용할 테스트 계층 | 예시 |
| --- | --- | --- |
| 값 해석, 입력 검증, 오류 변환 | Vitest 단위 테스트 | 잘못된 페이지 값, 201자 검색어, requestId 연결 |
| 컴포넌트의 권한·오류 동작 | React Testing Library | 비회원 댓글 제출 시 POST를 호출하지 않음 |
| 쿠키, 경로 이동, 프록시, 실제 사용자 흐름 | Playwright E2E | 로그인, 새로고침, 게시글 작성·수정·삭제 |
| DB 제약, Flyway, 트리거, 동시성 | PostgreSQL 통합 테스트 | 중복 좋아요, 24시간 조회 수 집계 |
| 화면 품질과 탐색적 확인 | 수동 배포 점검 | 모바일 배치, 키보드 포커스 순서, 실제 배포 환경의 핵심 기능 확인 |

## 회귀 테스트 규칙

운영 중 또는 검토에서 발견한 모든 결함은 다음 순서로 처리한다.

```text
문제 재현 → 실패하는 자동화 테스트 작성 → 최소한의 수정 → 테스트 통과 → 명세·테스트 연결표 갱신
```

회귀 테스트를 자동화할 수 없다면 사유, 환경, 수동 배포 점검 항목을 `release-checklist.md`에 기록한다.

## 완료 기준

- 관련 계약과 명세·테스트 연결 기록을 갱신했다.
- API 변경 시 입력 검증, 미인증, 권한 부족, 오류 동작을 검증했다.
- 프론트엔드 변경 시 `format:check`, 린트, 단위·컴포넌트 테스트, 빌드가 통과했다.
- 백엔드 변경 시 관련 검사가 통과했다.
- E2E 결과는 통과, 사유를 포함한 건너뜀, 해당 없음으로 구분한다. 건너뜀을 통과로 보고하지 않는다.
- 완료 보고에 변경 파일, 실행 명령과 결과, 남은 위험을 포함했다.

## 결정 필요 사항 (`DECISION_NEEDED`)

- E2E 환경을 실행할 CI 플랫폼과 보호 브랜치 정책.
- 격리된 PostgreSQL E2E 데이터베이스의 생성·초기화 방법.
- 지원 브라우저, 접근성 목표, 성능 허용 기준, 배포 책임자.
