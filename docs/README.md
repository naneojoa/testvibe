# 문서 안내: 무엇을 읽고 언제 사용하는가

이 폴더는 게시판을 만들고, 검사하고, 운영하기 위한 설명서 모음이다. 프로그램은 `.md` 파일을 실행하지 않는다. 개발자와 작업을 요청받은 AI가 문서를 읽고 코드·테스트·운영 작업에 적용한다. Markdown(`.md`)은 제목·표·코드 예제를 담는 텍스트 형식이며, VS Code의 미리 보기로 읽을 수 있다.

## 1. 전체 흐름

```text
무엇을 만들지 정하기: 화면·API·DB 명세
    ↓
어떤 원칙으로 만들지 정하기: 개발 지침·설계 결정 기록
    ↓
구현하고 변경 이유 기록하기: 코드·개선 구현 기록
    ↓
무엇을 검사할지 정하기: 테스트 시나리오·품질 검증 계획
    ↓
실제로 검사하고 증거 연결하기: 명세·테스트 연결표
    ↓
배포 전에 확인하기: 배포 점검표
    ↓
실행하고 운영하기: 백엔드 운영 안내
```

검증·테스트 에이전트를 나누어 사용할 때는 `quality-agents.md`의 절차를 추가로 적용한다.

## 3. 이 문서들은 어떻게 생겼는가

이름만 보고 Spring Boot·Vite·Gradle이 자동 생성한 문서라고 생각하면 안 된다. 이 문서들은 프로젝트의 요구사항·설계 선택·구현 경험·검증 절차를 정리한 프로젝트 문서다. 프로그램 빌드 결과나 자동 테스트 리포트와는 구분한다.

2026-10-21 확인 시 현재 작업 폴더에서는 Git 저장소 이력을 조회할 수 없었다. 따라서 각 파일의 최초 작성자, 생성 커밋, 최초 생성일, 작성 도구는 확정할 수 없다. 아래는 파일 내용에 남은 근거와 문서 목적을 구분한 설명이다.

| 문서 묶음 | 문서에서 확인되는 작성 배경 또는 기록 |
| --- | --- |
| API 명세 | 변경 이력에 2026-07-20 백엔드 분리·초기 계약, 2026-07-22 로컬 기동 문제, 2026-07-28 보안·트랜잭션·오류 처리 개선이 기록되어 있다. 이 날짜들이 파일 생성일이라는 뜻은 아니다. |
| 화면 명세 | 고객 협의용 초안으로 시작하는 문서이며, 사용자 흐름·설계 기준과 2026-07의 개발 진행 기록을 함께 담고 있다. |
| DB 설계서와 SQL 참고 자료 | 회원·게시글·댓글·좋아요·조회 수 요구사항을 설명과 SQL 형태로 정리한다. 최초 생성일이나 생성 도구는 문서만으로 확인할 수 없다. |
| 개선 구현 기록 | 2026-07-28 작업에서 바꾼 코드, 검증 결과, 미적용 항목을 남긴 기록이다. |
| 테스트 시나리오 | API를 정상·오류·경계·권한 사례로 나누고 검증 증거를 관리하기 위한 문서다. 2026-09-16 실행 스냅샷이 있으며 현재 실행 결과와는 다르다. |
| 개발 지침·품질 계획·연결표·배포 점검표 | 여러 작업에서 같은 개발·검증 기준을 반복 적용하기 위한 문서다. 파일 본문만으로 최초 작성 시점은 확인할 수 없다. |
| ADR 0001 | 프론트 상태, 쿠키 인증, 테스트 계층을 선택한 배경·결정·영향을 남긴 기록이다. 제목의 0001은 결정 번호이며 날짜가 아니다. |
| 에이전트 운영 가이드 | 별도의 검증 역할과 테스트 역할, 전용 스킬을 어떤 순서로 전달하고 사용할지 정리한 문서다. 자동 실행 설정 파일은 아니다. |
| 백엔드 운영 안내 | 개발자가 서버 실행과 환경 변수 준비를 반복할 수 있도록 정리한 문서다. |
| 이 안내 문서 | 2026-10-21 문서 역할·생성 배경·사용법 설명과 한글화 요청에 따라 추가했다. |

## 4. 처음 보는 사람의 추천 읽기 순서

1. `front-spec.md`: 사용자가 무엇을 할 수 있는지 이해한다.
2. `backend-api-spec.md`: 화면이 서버에 무엇을 요청하는지 확인한다.
3. `database-schema-spec.md`: 서버가 데이터를 어떻게 저장하는지 확인한다.
4. `engineering-playbook.md`: 구현 전에 지켜야 할 규칙을 확인한다.
5. `backend-operations.md`: 실행 환경을 준비한다.
6. `backend-api-test-scenarios.md` → `quality-validation-plan.md` → `spec-test-traceability.md`: 검사 항목·검사 방법·증거를 연결한다.
7. 배포 시 `release-checklist.md`를 사용한다. 설계 이유는 ADR, 과거 수정 내용은 개선 구현 기록에서 찾아본다.

## 5. 실제 사용 예: 게시글 수정 권한 변경

예를 들어 “작성자 또는 관리자만 수정 가능” 규칙을 변경하려 한다면 다음 순서로 작업한다. 이것은 사용 예시이며 현재 권한을 변경한다는 뜻은 아니다.

1. API 명세에서 현재 권한 규칙을 읽고 변경할 규칙을 확정한다.
2. 화면 명세에서 수정 버튼 표시와 권한 오류 안내도 영향을 받는지 확인한다.
3. 개발 지침을 적용해 서버 권한 검사와 화면 처리를 수정한다. DB 변경이 필요하면 새 Flyway 파일을 추가한다.
4. 테스트 시나리오에서 작성자·다른 회원·관리자·비회원의 기대 결과를 갱신한다.
5. 관련 테스트를 작성·실행하고 명세·테스트 연결표에 증거를 연결한다.
6. 개선 구현 기록에 실제 변경과 검증 결과를 남기고, 배포할 때 점검표를 확인한다.

문서만 바꾼다고 서버의 권한이 바뀌지는 않는다. 반대로 코드만 바꾸고 API·화면 계약과 테스트를 그대로 두어도 안 된다.

## 6. 문서를 읽을 때 구분할 것

- **계약**은 앞으로 구현이 지켜야 할 약속이고, **작업 기록**은 특정 시점에 수행한 내용이다.
- `front-spec.md`의 협의 전 초안 표시와 `DECISION_NEEDED`는 미확정 사항을 뜻한다. 확정된 기능처럼 구현하지 않는다.
- `IMPLEMENTED`는 자동화 코드가 있다는 뜻이며 `PASS`는 해당 실행에서 통과했다는 뜻이다. `SKIP`, `NOT_RUN`, `BLOCKED`는 통과가 아니다.
- 요약 연결표와 상세 시나리오에는 기록 시점·상세 수준 차이가 있을 수 있다. 이번 번역에서 기존 판정을 재평가하지 않았으므로 최신 테스트 코드와 실행 증거로 확인한다.
- “테스트 9개 성공” 같은 과거 기록은 현재 버전의 통과 보증이 아니다. 배포 대상에서 다시 실행해야 한다.
- `create_table.md`는 참고 문서다. 실제 DB 변경 이력은 `backend/src/main/resources/db/migration/`에서 관리한다. 적용한 마이그레이션은 고치지 않고 새 파일을 추가한다.
- 파일명, API 경로, JSON 키, 코드, 명령어, 환경 변수, 오류 코드와 테스트 ID는 실행·참조에 필요하므로 영문을 유지한다. 설명과 제목·표 항목은 한글로 읽을 수 있게 정리했다.
