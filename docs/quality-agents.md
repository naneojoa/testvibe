# 검증·테스트 에이전트 운영 가이드

## 역할

| 역할 문서 | 전용 스킬 | 책임 | 산출물 |
| --- | --- | --- | --- |
| `.agents/roles/board-validator.md` | `board-validate` | 명세·구현 비교, 검증 계획, 증거 재검토 | 검증 계획과 최종 검토 보고서 |
| `.agents/roles/board-tester.md` | `board-test` | 테스트 보완, 실행, 실패 재현, 정리 | 테스트 변경, 실행 보고서 |

역할과 절차는 모두 마크다운으로 작성했다. `.agents/roles/*.md`는 이 프로젝트에서 정한 역할 문서이며, 파일만 두었다고 에이전트가 자동 등록되거나 실행되지는 않는다. 호출할 때 부모 대화가 별도 에이전트 두 개에 각 역할 문서와 스킬을 지정한다. 모델과 권한은 부모 세션을 상속한다. 역할별 수정 제한은 작업 지침이다. 제품 코드 수정은 별도 작업으로 요청한다.

## 단계별 사용

1. 프로젝트 루트에서 두 역할 문서와 두 스킬의 경로를 확인하고, 별도 하위 에이전트 두 개를 사용할 수 있는지 확인한다.
2. 부모 대화는 범위, 소스 상태, 실행 ID를 정한다. 보고서는 `docs/validation/<run-id>/`에 저장한다. Git 메타데이터가 없으면 커밋 대신 해당 한계와 대상 파일을 기록한다.
3. 첫 번째 검증 에이전트가 `board-validator.md`와 `board-validate` 스킬로 명세와 구현을 비교하고 `validation-plan.md`를 작성한다. 시나리오 ID, 계약 위치, 기대 결과, 우선순위, 필요한 테스트 계층과 합격 기준을 포함한다.
4. 부모가 계획을 두 번째 테스트 에이전트에 전달한다. 테스트 에이전트는 `board-tester.md`와 `board-test` 스킬에 따라 환경을 확인하고 테스트를 작성·실행하여 `test-results.md`를 작성한다. 격리 DB가 확인되지 않으면 데이터 변경 E2E는 BLOCKED로 기록하고 독립적인 검사는 계속한다.
5. 부모가 결과와 산출물을 검증 에이전트에 전달한다. 실제 검증문과 실행 증거를 확인하고 `validation-review.md`에 판정을 남긴다.
6. 부족한 증거만 테스트 에이전트에 재요청한다. 동일 장애가 새로운 근거 없이 두 번 반복되면 재개 조건을 보고한다. 제품 결함은 수정 작업으로 인계한다.

부모 대화는 전달과 조율을 맡는다. 전문 에이전트는 위 두 개이며 세 번째 전문 에이전트는 필요하지 않다. 최초 코드 조사와 환경 확인은 병렬화할 수 있지만 계획 전달과 최종 판정은 순서를 지킨다. 테스트 파일과 공유 DB는 테스트 에이전트 한 곳에서만 변경한다.

## 복사해서 사용할 요청

```text
게시판의 현재 구현을 검증하기 위해 별도 하위 에이전트 두 개를 사용해줘.
첫 번째 검증 에이전트는 .agents/roles/board-validator.md와
.agents/skills/board-validate/SKILL.md를 읽고 검증 계획을 작성해줘.
두 번째 테스트 에이전트는 .agents/roles/board-tester.md와
.agents/skills/board-test/SKILL.md, 검증 계획을 읽고 테스트를 보완·실행해줘.
그 결과를 검증 에이전트에 전달해 증거를 독립적으로 검토해줘.
docs/quality-agents.md의 전달 절차와 파일 소유권을 따라줘.
제품 코드는 수정하지 말고 격리 DB가 확인되지 않은 데이터 변경 테스트는 실행하지 마.
보고서는 docs/validation/<이번 실행 ID>/에 남겨줘.
필수 항목이 BLOCKED, SKIPPED, NOT RUN이면 전체 PASS로 선언하지 마.
```

스킬을 직접 사용하려면 `$board-validate` 또는 `$board-test`를 명시한다. 스킬 호출 자체는 별도 에이전트 생성이 아니다.

하위 에이전트를 사용할 수 없는 클라이언트에서는 같은 프로젝트를 연 두 대화에 각 역할 문서와 스킬을 지정하고, 저장된 검증 계획과 테스트 보고서를 순서대로 전달한다. 자동 위임이 설정되었다고 표현하지 않는다.

## 증거와 완료 기준

- 계획: 시나리오 ID, 계약·구현 위치, 기대 결과, 필요한 실행 증거.
- 테스트: 명령·디렉터리·종료 코드, 환경, 통과·실패·건너뜀 수, 재현 절차, 산출물, 정리 결과.
- 검토: 확인한 증거, 결함과 미검증 영역, 변경 파일, 재개 조건, 범위 내 최종 판정.
- 모든 계획 항목에 결과 또는 미실행 사유가 있으면 검증 보고를 완료할 수 있다. 전체 PASS는 모든 필수 합격 기준이 실행 증거로 충족되어야 한다.
- 현재 설정과 테스트 수는 실행마다 재확인한다. HTTP 응답, H2 테스트, 관리자 메뉴 표시를 각각 DB 전체 정상, PostgreSQL 동시성 보장, API 권한 검증으로 확대 해석하지 않는다.
