# 프론트엔드 UX/UI 설계안 (협의용 초안)

> 상태: 고객 협의 전 초안  
> 대상: 게시글·댓글 중심의 반응형 커뮤니티 웹  
> 연계 명세: `backend-api-spec.md`

## 1. 이 문서의 목적과 범위

이 문서는 고객과 화면 구조·사용 흐름·운영 원칙을 합의하고, 구현이 계속 따라야 할 프론트 설계 기준을 기록한다. 구현 전 아래의 **확정 필요 사항**을 먼저 결정하고, 확정된 내용은 본 문서와 API 명세에 반영한다.

지속적인 UX·상태 관리·모듈 경계와 변경 사유는 이 문서에 남긴다. 특정 작업에서 수정한 파일과 실행한 명령 같은 구현 이력은 `implementation-improvements.md`에 기록하고, 이 문서의 개발 진행 기록에는 사용자 경험이나 설계 기준에 영향을 주는 결과만 요약한다.

현재 제안은 "읽고 찾고 참여하기 쉬운 일반 커뮤니티 게시판"을 기준으로 한다. 특정 연령대, 유료 기능, 광고, 파일 첨부 기능은 아직 전제하지 않는다.

## 2. 브랜드 방향: 잇글

### 브랜드 정의

- **서비스명(작업명)**: **잇글**
- **한 줄 메시지**: 생각을 잇는 글의 공간
- **핵심 인상**: 믿을 수 있고 차분하지만, 처음 온 사용자도 부담 없이 참여할 수 있는 커뮤니티
- **말투**: 짧고 다정하며 단정하게 쓴다. 과한 유행어·명령형·기술 용어를 피한다.

`잇글`은 협의와 구현을 위한 작업명이며, 상표·도메인 사용 가능 여부는 별도로 확인해야 한다.

### 시각 토큰

| 용도 | 값 | 사용 원칙 |
| --- | --- | --- |
| 주요 강조색 | `#2563EB` | 주요 행동, 활성 탭, 링크 |
| 보조 강조색 | `#EFF6FF` | 선택 상태, 보조 버튼 배경 |
| 기본 글자색 | `#172033` | 제목과 핵심 본문 |
| 보조 글자색 | `#667085` | 작성자·날짜·조회 수 등 보조 정보 |
| 화면 배경색 | `#F6F8FB` | 페이지 배경 |
| 오류색 | `#DC2626` | 삭제, 오류, 위험 행동 |

- 모서리 반경은 8~14px, 간격은 4px 기반의 8px 그리드를 사용한다.
- 한 화면에서 강조 색상은 주요 강조색 하나를 우선 사용한다.
- 글자체는 `Pretendard`, `Noto Sans KR`, 시스템 sans-serif 순으로 사용한다.

## 3. 제품 원칙

1. **읽기 우선**: 목록에서 원하는 글을 빠르게 찾고, 상세에서 본문에 집중한다.
2. **예측 가능성**: 작성·수정·삭제·좋아요의 결과와 권한 제한을 사전에 명확히 보여 준다.
3. **모바일 우선 반응형**: 모바일에서 검색, 글 읽기, 댓글 작성이 끊기지 않아야 한다.
4. **접근성 기본값**: 충분한 명도 대비, 키보드 조작, 명확한 오류 메시지, 44px 이상의 터치 영역을 적용한다.
5. **서버를 기준으로 한 상태**: 게시글·댓글·좋아요·로그인 사용자 정보는 서버 응답을 기준으로 갱신한다.

## 4. 정보 구조

```text
홈 / 게시글 목록
├── 검색 결과 (검색어 및 정렬 유지)
├── 게시글 상세
│   ├── 게시글 좋아요
│   ├── 댓글 목록 (트리)
│   └── 댓글·답글 작성 및 좋아요
├── 게시글 작성 / 수정
├── 로그인 / 회원가입
├── 내 정보
└── 관리자 회원 관리 (ADMIN만 노출)
```

## 5. 핵심 사용자 흐름

### 비회원: 탐색 후 참여

1. 게시글 목록에서 검색하거나 정렬한다.
2. 게시글 상세와 댓글을 읽는다.
3. 좋아요·글쓰기·댓글 작성 시 로그인 안내를 받는다.
4. 로그인 후 원래 보던 위치 또는 요청한 행동으로 돌아간다.

### 회원: 글과 댓글 참여

1. 로그인 상태로 목록·상세를 이용한다.
2. 글쓰기 또는 댓글 입력란에 내용을 작성한다.
3. 클라이언트에서 글자 수와 필수값을 즉시 안내한다.
4. 서버 성공 응답 후 목록/상세를 최신 상태로 갱신하고 완료 토스트를 표시한다.

### 관리자: 회원 관리

1. 프로필 메뉴에서 관리자 메뉴로 이동한다.
2. 회원 목록을 페이지 단위로 확인한다.
3. 역할 변경·삭제는 대상과 결과를 명시한 확인 창을 거친다.
4. 자신의 역할 변경 및 계정 삭제는 UI에서도 비활성화하고, 서버 오류도 처리한다.

## 6. 화면별 설계

| 화면 | 주요 구성 | UX 기준 |
| --- | --- | --- |
| 게시글 목록 | 검색, 정렬, 글쓰기, 목록, 페이지네이션 | 검색어·정렬·페이지를 URL 쿼리로 유지한다. |
| 게시글 상세 | 제목, 작성자, 날짜, 조회/좋아요, 본문, 액션, 댓글 | 작성자/관리자에게만 수정·삭제를 노출한다. |
| 글 작성·수정 | 제목, 본문, 취소/저장 | 제목 1~200자, 본문 1~10,000자 제한과 오류를 인라인으로 표시한다. |
| 로그인·회원가입 | 이메일, 비밀번호, 닉네임, 제출 | 중복 제출을 막고, 필드 오류와 인증 실패를 구분한다. |
| 내 정보 | 닉네임 수정, 역할 표시, 로그아웃 | 이메일은 식별 정보로 읽기 전용 표시를 권장한다. |
| 관리자 회원 | 회원 테이블, 역할, 관리 액션, 페이지네이션 | 파괴적 작업은 확인 창을 거치고 결과를 즉시 반영한다. |

## 7. 비주얼 시스템 초안

- **분위기**: 브랜드 "잇글"의 차분하고 신뢰감 있는 정보형 서비스. 장식보다 위계와 가독성에 집중한다.
- **색상**: 위 브랜드 토큰을 사용하고, 성공·경고·오류는 의미 색상으로 제한한다.
- **타이포그래피**: 본문 16px, 본문 줄간격 1.7, 보조 정보 13~14px, 제목은 24~32px 범위로 시작한다.
- **레이아웃**: 데스크톱 콘텐츠 최대 폭 1,120px. 모바일 가로 여백 16px, 데스크톱 24px 이상.
- **컴포넌트**: 버튼, 입력, 배지, 탭, 카드/목록 행, 모달, 토스트, 스켈레톤, 빈 상태를 재사용 단위로 정의한다.
- **댓글 트리**: 무제한 답글이라도 화면 들여쓰기는 최대 2단계까지만 강조한다. 이후 깊이는 세로선과 "답글" 표기로 표현한다.

## 8. 상태와 오류 처리

| 상황 | 화면 처리 |
| --- | --- |
| 최초 로딩 | 목록·본문 형태를 유지한 스켈레톤 표시 |
| 결과 없음 | 검색어를 보여 주고 검색 초기화 행동 제공 |
| 비로그인 액션 | 로그인 화면으로 안내하고, 가능한 경우 원래 위치를 보존 |
| 입력 검증 실패 | `fieldErrors`를 각 입력칸 아래에 표시 |
| 권한 없음 | 버튼은 숨기거나 비활성화하되, 서버의 403도 "권한이 없습니다"로 안내 |
| 중복 좋아요 | 낙관적 업데이트를 되돌리고 "이미 좋아요한 항목입니다" 안내 |
| 삭제 불가 댓글 | 자식 댓글 존재 사유와 먼저 처리할 행동을 설명 |
| 네트워크 실패 | 재시도 버튼과 짧은 오류 메시지 제공 |

## 9. 프론트엔드 기술 설계 기준

```text
pages/          화면과 라우트
features/       auth, posts, comments, users, admin 도메인 단위
components/ui/  Button, Input, Modal, Toast, Pagination 등 재사용 UI
components/layout/ Header, ContentContainer
lib/api/        fetch 래퍼, JSON 응답/오류 변환
stores/         Zustand: 로그인 사용자, 모달, 토스트, 테마
```

- TanStack Query: 게시글, 댓글, 좋아요, 내 정보, 회원 목록 등 서버 데이터.
- Zustand: 로그인 사용자 표시 상태, 모달, 토스트, 테마 같은 클라이언트 상태.
- API 클라이언트: `credentials: 'include'`를 기본값으로 하며, JWT를 localStorage에 저장하지 않는다.
- API 클라이언트: 상태 변경 요청 전에 `/api/auth/csrf`를 호출하고, JavaScript에서 읽은 `XSRF-TOKEN` 쿠키 값을 서버가 알려 준 헤더에 포함한다. 응답 본문의 XOR 마스킹 토큰을 헤더 값으로 사용하지 않는다.
- 앱 시작: `GET /api/users/me` 호출로 로그인 사용자를 확인한다. 401은 비로그인 상태로 정상 처리한다.
- 응답: 공통 `{ data: ... }` 래퍼를 API 계층에서 해제하고, 오류 응답은 공통 타입으로 변환한다.
- 오류: 서버의 `requestId`를 보존하고 미분류 서버 오류 안내에 오류 번호를 표시한다. 오류 토스트는 보조기기에 즉시 전달되도록 `role="alert"`를 사용한다.

### 구조 개선 및 최적화 의사결정 (2026-07-25)

현재 `frontend/src`는 `pages`, `features`, `components`, `lib`, `stores`로 나뉘며, 소규모 애플리케이션으로서는 단순하고 탐색하기 쉽다. 서버 데이터는 TanStack Query, 로그인 사용자와 토스트 같은 클라이언트 상태는 Zustand로 구분되어 있다. 이 기본 경계는 유지하며, 폴더 수를 늘리는 것 자체를 개선으로 판단하지 않는다.

#### 현재 확인한 구조상 개선 후보

- `features/*/api.ts`는 도메인별 API 경계를 제공하지만, 댓글 컴포넌트와 mutation 조정 로직은 `PostDetailPage.tsx`에 집중되어 있다.
- 게시글·댓글·회원·관리자 API가 JSON 요청 생성 함수를 `features/auth/api.ts`에서 가져온다. JSON 요청 생성은 인증 기능이 아니라 공통 HTTP 책임이다.
- `stores/ui-store.ts`에는 서로 분리된 Zustand Store가 선언되어 있지만 파일 이름과 달리 인증 사용자 상태도 포함한다.
- `App.tsx`는 Provider, 세션 초기화, 라우팅, 권한 Route를 함께 관리한다.
- 공통 타입과 UI 컴포넌트는 각각 `types.ts`, `components/ui.tsx` 한 파일에 모여 있다.
- TSX와 CSS가 긴 한 줄 형태여서 lint 통과 여부와 별개로 diff 검토, 중단점 디버깅, 충돌 해결이 어렵다.
- 배포 방식이 빌드 산출물 커밋을 요구하지 않는다면 `frontend/node_modules/`, `frontend/dist/`, `frontend/coverage/`를 Git에서 제외해야 한다.

#### 적대적 검토 결과

전면적인 기능별 수직 분리 구조 전환, 모든 타입의 도메인별 분산, 모든 UI 컴포넌트의 개별 파일화, `App.tsx`의 다중 파일 분리는 현재 규모에서 보류한다. 현재 페이지는 6개이고 공통 타입과 UI 파일도 작기 때문에, 이를 일괄 분리하면 기능적 이득 없이 파일 수, import 경로, 탐색 비용만 증가할 수 있다.

페이지가 라우팅, 성공 후 이동, 토스트, Query 무효화를 조정하는 것도 현재 단계에서는 허용한다. 동일 로직이 여러 화면에서 반복되거나 독립 테스트가 어려운 경우에만 기능 훅으로 이동한다. 단, 게시글 상세의 댓글 트리와 댓글 작성기는 한 페이지에서 독립 책임이 명확하므로 우선 분리 후보로 본다.

#### 적용 우선순위

1. JSON 요청 생성 함수를 `auth` 기능에서 공통 API 계층으로 이동해 기능 간 잘못된 의존 방향을 제거한다. 2026-07-28 적용했다.
2. TSX·CSS 자동 포맷팅을 도입하되 기능 리팩터링과 별도 변경으로 수행한다. 2026-07-28 Prettier와 검사 명령을 추가했다.
3. 실제 배포 및 Git 추적 방식을 확인한 뒤 프론트 생성물을 `.gitignore`에 추가한다. 현재 배포가 산출물 커밋을 요구하지 않아 2026-07-28 적용했다.
4. `PostDetailPage`에서 댓글 트리와 댓글 작성기만 선택적으로 분리한다. 2026-07-28 `features/comments/CommentSection.tsx`로 분리했다.
5. 인증 Store, Router, 공통 타입, 공통 UI는 실제 크기와 변경 충돌이 증가할 때 분리한다.

#### 성능 최적화 판단

2026-07-25 프로덕션 빌드 기준 결과는 JavaScript 304.31KB(gzip 95.79KB), CSS 5.84KB(gzip 1.91KB)다. 현재 번들 크기만으로 라우트 코드 분할이나 CSS 분할을 필수로 판단하지 않는다. 관리자 화면에 대형 테이블·차트가 추가되거나 Markdown·리치 텍스트 편집기 도입 후 초기 JavaScript와 실제 사용자 지표가 악화될 때 경로별 지연 로딩을 적용한다.

댓글은 전체 조회, 무제한 깊이, 재귀 계산·렌더링, mutation 성공 후 전체 Query 무효화가 결합되어 있다. 다만 실제 데이터 규모를 확인하지 않고 `React.memo`, 가상화, mutation 중앙화를 먼저 적용하지 않는다. 댓글 100·500·1,000개와 깊은 답글 트리를 기준으로 응답 크기와 React Profiler 결과를 측정한 후, 백엔드 페이지네이션 또는 "답글 더 보기" API와 함께 최적화한다.

좋아요 수는 PostgreSQL 트리거가 최종 상태를 관리하고 현재 응답에 `likedByMe`와 변경된 `likeCount`가 없으므로, 프론트에서 임의로 낙관적 캐시 값을 계산하지 않는다. 정확한 상태 응답 계약이 마련되기 전까지 성공 후 refetch를 유지한다. 검색은 제출 방식이므로 debounce를 추가하지 않으며, 다음 페이지 prefetch는 실제 이동률과 API 비용을 확인한 뒤 결정한다.

#### 의사결정 원칙

- 폴더가 정교해 보이는지가 아니라 현재 변경 비용과 장애 가능성을 줄이는지를 기준으로 삼는다.
- 실제 중복, 파일 충돌, 테스트 곤란, 측정된 성능 저하가 없는 추상화는 미리 추가하지 않는다.
- 프론트 단독 최적화로 해결할 수 없는 댓글 페이지네이션과 좋아요 상태 계약은 백엔드 API와 함께 설계한다.
- 구조 리팩터링보다 현재 확인된 API 오류 처리, 인증, 트랜잭션 같은 제품 결함을 우선한다.

| --- | --- | --- | --- |

## 11. 협의 전에 확정할 질문

다음은 구현 방향이나 고객 경험을 실질적으로 바꾸므로 고객에게 확인이 필요하다.

1. 주요 사용자는 누구이며, PC와 모바일 사용 비중은 어느 쪽이 큰가?

#### 미수행 액션 아이템: 실제 백엔드 통합 점검

다음 항목은 정적 검사·컴포넌트 테스트·빌드와 Vite 첫 화면 확인에는 포함되지 않았으며, Spring Boot와 PostgreSQL을 함께 실행한 상태에서 수동으로 검증해야 한다.

- [ ] 비회원 상태에서 게시글 목록을 조회하고 검색어·정렬·페이지 변경이 URL 쿼리 및 서버 결과와 일치하는지 확인한다.
- [ ] 비회원 상태에서 게시글 상세와 댓글 목록을 조회하고, 인증이 필요한 행동이 로그인 화면으로 안내되는지 확인한다.
- [ ] 새 일반 회원을 가입시키고 로그인·로그아웃이 정상 동작하는지 확인한다.
- [ ] 로그인 회원으로 게시글을 작성·수정·삭제하고 목록과 상세 Query가 최신 상태로 갱신되는지 확인한다.
- [ ] 댓글과 답글을 작성·수정·삭제하고 댓글 트리와 삭제 제한 안내가 서버 정책과 일치하는지 확인한다.
- [ ] 게시글과 댓글 좋아요를 처리하고, 같은 대상에 다시 좋아요할 때 `409 ALREADY_LIKED`가 사용자용 중복 좋아요 안내로 표시되는지 확인한다.
- [ ] 설정한 ADMIN 계정으로 로그인하고 `/admin/users`의 회원 목록, 페이지네이션, 역할 변경 및 삭제 권한을 확인한다.
- [ ] 로그인 후 브라우저를 새로고침해도 HttpOnly 쿠키 기반 로그인 상태가 유지되는지 확인한다. 개발자 도구에서는 쿠키 값 자체를 읽는 대신 요청에 쿠키가 포함되고 사용자 정보가 복원되는지를 확인한다.
- [ ] 브라우저 개발자 도구의 Network 탭에서 프론트 API 요청 URL이 `http://localhost:5173/api/...`이고 Vite 프록시를 통해 8080 백엔드 응답을 받는지 확인한다.
- [ ] 모바일·데스크톱 화면에서 목록, 상세, 댓글, 로그인, 관리자 화면의 레이아웃과 오류 메시지를 확인한다.

문제 발생 시 다음 순서로 확인한다.

- `non-empty schema` 또는 Flyway 이력 오류: `community` DB가 완전히 재생성됐고 Flyway가 V1부터 적용됐는지 확인한다.
- 환경변수 누락 오류: Dashboard 실행 구성이 `.env.local`을 읽는지 확인한다. 터미널 `bootRun` 방식이면 환경변수를 설정한 동일한 백엔드 터미널에서 실행했는지 확인한다.
- 로그인 쿠키가 유지되지 않음: `local` 프로필, `COOKIE_SECURE=false`, 브라우저 접속 주소가 `http://localhost:5173`인지 확인한다.
- 8080 또는 5173 포트 충돌: `Get-NetTCPConnection -State Listen -LocalPort 8080,5173`으로 점유 프로세스를 확인하고, 이 프로젝트의 실행 프로세스인지 확인한 후 종료한다.
- API가 500을 반환함: 백엔드 Debug Console에서 최초 `Caused by`와 요청 매핑 오류를 확인한다. 공통 오류 응답만으로 원인을 추측하지 않는다.

점검 종료 시 프론트엔드 터미널에서 `Ctrl+C`로 Vite를 종료한다. 백엔드를 Spring Boot Dashboard로 실행했다면 Dashboard의 Stop 버튼으로 종료하고, 터미널 `bootRun`으로 실행했다면 백엔드 터미널에서 `Ctrl+C`를 누른다.

이 액션 아이템의 목적은 현재 소스와 API 계약을 실제 로컬 환경에서 검증하는 것이다. 점검 중 결함이 발견되면 즉석에서 계약을 변경하지 않고 원인, 영향 범위, 수정 및 회귀 테스트를 별도 작업으로 기록한다.
